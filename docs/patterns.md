# Патерни проєктування

| Патерн | Група GoF | Яку проблему розв'язує | Де застосовується |
|---|---|---|---|
| Strategy | Поведінковий | Алгоритмів генерації та пошуку шляху багато, і без патерна довелося б писати великий if/else. Strategy виносить кожен алгоритм в окремий клас із спільним інтерфейсом, тому алгоритми взаємозамінні й додаються без зміни наявного коду. | GeneratorAlgorithm (Backtracker, Prim, Kruskal), SolverAlgorithm (BFS, A*, правило руки) |
| Factory Method | Породжувальний | Код не повинен залежати від конкретних класів (RectGrid, HexGrid, конкретні алгоритми). Фабрика створює потрібний об'єкт за назвою, тому додавання нового типу сітки не вимагає змін у решті програми. | MazeFactory |
| Observer | Поведінковий | Для покрокової візуалізації алгоритм має повідомляти про кожен крок, але не повинен знати про графіку. Observer дозволяє підписати на події будь-якого слухача (інтерфейс, лог, статистику) без зв'язку з алгоритмом. | StepObserver, SolverAlgorithm |
| Facade | Структурний | Ядро на C++ складне, а Python-інтерфейсу потрібні лише прості операції. Facade надає єдину точку входу (generate, solve, getStats) і приховує внутрішню складність та деталі C++/Python-мосту. | MazeFacade, bridge.cpp |

## Зв'язок з принципами SOLID

- S (Single Responsibility): кожен клас має одну задачу (сітка зберігає стіни, генератор будує лабіринт, розв'язувач шукає шлях).
- O (Open/Closed): нові алгоритми та сітки додаються через нові класи, без зміни старих (Strategy, Factory).
- L (Liskov Substitution): будь-який нащадок Grid або SolverAlgorithm можна підставити замість базового типу.
- I (Interface Segregation): інтерфейси малі й цільові (GeneratorAlgorithm, SolverAlgorithm, StepObserver).
- D (Dependency Inversion): високорівневий код працює з абстракціями (Grid*, SolverAlgorithm*), а не з конкретними класами.
